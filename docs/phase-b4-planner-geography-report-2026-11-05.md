## 1. 原有规划器问题

B0 审查发现的核心问题（P1）：规划器生成的行程草案完全无视地理距离。`planner-service.js` 的 `planTrip` 只按主题/季节打分排序、按建议天数贪心分配日期，不做任何距离检查。本轮用表单真实生成 3 天草案复现了该问题：

- DAY 1 布达拉宫（拉萨）→ DAY 2 成都大熊猫繁育研究基地 → DAY 3 承德避暑山庄。
- 拉萨→成都直线 1256 公里，成都→承德直线 1683 公里，相邻两天连续跨越两个大区，全程无任何提示。

其他既有问题：

- 同一天、相邻日期、跨省跳跃均无检测；行程顺序是否绕路无判断。
- 目的地坐标只存在于 shard 的 `location` 字段，规划器加载的索引（`destinations-index.json`）没有坐标，页面无法计算距离。
- 行程数据结构为逐日单目的地（每天 1 个目的地），同一天多个景点在当前模型下不会出现，但检测逻辑应防御性覆盖。

本轮**不改** `planTrip` 的生成排序（见第 11 节遗留问题），只做检测 + 提示 + 用户确认式重排。

## 2. 地理计算方法和公式

新增纯函数模块 `assets/js/services/planner-geo.js`（无 DOM、无网络，与 `planner-service`/`planner-edit` 同构，可 Node 单测）。

**Haversine 球面直线距离**（地球半径 R = 6371 km）：

```
a = sin²(Δφ/2) + cos φ1 · cos φ2 · sin²(Δλ/2)
d = 2R · arcsin(√a)
```

其中 φ 为纬度（弧度）、λ 为经度（弧度）。`haversineKm(a, b)` 任一坐标缺失或非法（纬度 ±90、经度 ±180 以外）返回 `null`，调用方标记为无法计算，不编造。

**严格区分**：页面只展示"直线距离"，并在行程底部注明"距离为目的地之间的直线距离，不等于实际道路距离"。**不编造道路距离与交通时间**，提示文案只写"建议提前安排交通""预留充足的交通时间"，不写任何小时数。

## 4. 合理性检测规则及阈值

阈值集中在 `planner-geo.js` 的 `GEO` 对象，页面只读检测结果，不散落阈值。判定依据是**实际地理距离**，不只看是否跨省。

**相邻两天（过夜转移）**——校准实测：

| 直线距离 | 级别 | 校准案例 |
|---|---|---|
| ≤ 300 km | 正常 | 宏村→黄山 22km、乌镇→西湖 65km、成都→峨眉 156km |
| 300–800 km | 提示 | 北京→平遥 475km、北京→沈阳 629km、九寨沟→稻城 637km |
| 800–1500 km | 警告 | 北京→上海 1069km、拉萨→成都 1256km（B0 案例）、喀什→喀纳斯 1358km（同省亦远，证明不只看跨省） |
| > 1500 km | 严重 | 哈尔滨→亚龙湾 3440km、成都→承德 1683km |

**同一天多个目的地**（防御性，当前模型每天 1 个目的地）：≤80km 正常；80–200km 提示；200–400km 警告；>400km 严重。同日期的两条不走相邻规则（由同日检测覆盖，避免同一对地点重复提示）。

**绕路**：连续三天 A→B→C，若经 B 的路程 > A→C 直达的 2 倍，且多出 >300km，提示"第 X 天可能绕路"。实测：北京→上海→沈阳，经上海 2256km vs 直达 629km（3.6 倍，多 1627km）触发。

**顺路重排建议**：最近邻顺序（首日固定为出发点），比当前顺序省出 >200km 且 >20% 时才建议。实测：九寨沟→上海→成都（3319km）→ 九寨沟→成都→上海（1935km），省 1384km（42%）。

## 5. 提示、警告、严重三级规则

| 级别 | 含义 | 文案示例 |
|---|---|---|
| 提示（info） | 距离较远，建议提前安排交通 | "两地相距约 491 公里（直线距离），建议提前安排两地之间的交通。" |
| 警告（warn） | 行程衔接较困难，建议调整 | "「布达拉宫」到「成都大熊猫繁育研究基地」直线距离约 1256 公里。衔接较困难，建议调整顺序，或为这段转移预留充足的交通时间。" |
| 严重（severe） | 明显不符合常规旅行安排，需要用户确认 | "相邻两天安排如此远的跨越不符合常规旅行安排，请确认是否确实如此，或调整行程。" |

交互原则：**只提示，不限制**。提示行内展示在相关日期之后（相邻转移附在后一天、绕路附在中间一天、缺坐标附在该天），不遮挡原有编辑按钮；每条提示有"知道了"按钮，会话内忽略（不持久化、不改行程数据结构）；跨区域行程用户点"知道了"即视为接受，行程保持原样。重排建议为独立面板（行程总直线距离、节省公里与百分比、建议顺序列表），"应用此顺序"按钮是唯一的确认动作，点之前行程不做任何改变；"暂不调整"将会话内隐藏该建议（行程签名变化后可再次出现）。

## 10. 性能影响

- 地理计算为纯本地逻辑，无网络请求、无新依赖。分析为 O(n²) 最坏（同日分组两两比较），n ≤ 30 天时可忽略；最近邻重排同为 O(n²)。每次 `renderPlan` 重算一次，无可感知的渲染延迟。
- 索引增加 `location` 后 27815 → 31570 字节（+3755 字节，+13.5%），单次加载；规划器页面不新增请求（坐标随索引一次取回）。
- SW 缓存：`planner-geo.js` 已加入 CORE 清单，版本同步递增至 `20261105d`，旧缓存不会继续展示旧版页面。

## 11. 遗留问题

1. **生成器本身仍不感知地理**：`planTrip` 按主题/季节打分排序，仍会生成拉萨→成都→承德这类草案，B4 只在生成后提示与建议重排。是否让生成器按地理聚类排序，需总设计师决策（会影响现有排序单测与"主题匹配者优先"的既定语义）。
2. **交通时间未提供**：只有直线距离。北京→上海（1069km，高铁可达）与拉萨→成都（1256km，需飞机）同为警告级，距离无法区分交通可达性；按任务书不编造交通时间，暂不引入高铁/航班数据。
3. **"知道了"仅会话内有效**：刷新后提示重新出现。持久化接受状态需改行程数据结构，本轮未做。
4. **K80 真机、读屏、旧客户端 SW 线上升级（20261105c→d）未观测**（与 B1–B3 相同遗留）。
