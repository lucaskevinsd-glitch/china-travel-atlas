## 1. 原生成器排序逻辑

`planner-service.js` 的 `planTrip`（B4 之前）：

1. 按主题（+10）、季节（+6）、省份（+3）给候选目的地打分。
2. 按分数降序、同分按名称（`localeCompare('zh')`）排序。
3. 贪心分配：按排名依次给每个目的地 `min(建议天数上限, 剩余天数)`，至少 1 天；剩余天数并入最后一个。
4. 按分配顺序逐日生成行程（日期连续）。

问题：排序完全无视地理。无筛选时全部 0 分，顺序即字母顺序，选出的前 N 个目的地地理上随机。B4 报告的真实生成案例（表单，2026-11-02，3 天）：

- **布达拉宫 → 成都大熊猫繁育研究基地 → 承德避暑山庄**，总直线距离 2939km，B4 检出 1 警告（拉萨→成都 1256km）+ 1 严重（成都→承德 1683km）。

生成器入口唯一：`pages-planner.js` 表单提交时调用 `planTrip(index, input)`。行程编辑（`planner-edit.js`）与 B4 检测（`planner-geo.js`）均独立于生成器。

## 2. 新增地理感知算法说明

**设计**：在现有打分排序之后、贪心分配之前，增加一步地理排序。复用 B4 的 `planner-geo.js`，不新建第二套距离计算。

`planner-geo.js` 新增 `orderByGeography(scored)`：

1. **按分数分层**：输入已按分数降序，连续同分者为一层。分层顺序不变（用户偏好优先于地理）。
2. **每层内最密集点出发、最近邻链**：有坐标者中，取层内 300km（复用 B4 `GEO.adjacent.info`，不引入新阈值）邻居最多的目的地为起点，并列时取原顺序在先者；随后反复取最近的未访问点，直到链完本层。
3. **无坐标者**：保留在本层末尾、相对顺序不变，不参与距离优化，但仍可正常进入行程；天数不足时优先保障地理连续的链路。

**为什么起点重要**（实测）：无筛选时字母顺序首位是布达拉宫（拉萨），从它出发的最近邻链首跳 912km（稻城亚丁），仍是警告级；而 300km 内邻居最多的点是杭州西湖/乌镇（各 6 个），从那里出发的 5 站链仅 618km。因此起点取"最密集点"而非字母首位。

**`planTrip` 的改动**（最小必要）：

- 签名改为 `planTrip(candidates, input, geoApi)`，第三参数可选。页面传入 `CTA.plannerGeo`；不传或无 `orderByGeography` 时退回原有分数+名称顺序（向后兼容，现有单测无需改动）。
- `input.pinned`（可选，目的地 ID 数组）：用户明确指定的目的地，按给定顺序置于最前且不参与重排、不得被删除；其余候选仍按分数分层地理排序。当前表单无目的地选择器，该参数为 API 级能力（供未来界面使用），本轮不增加任何用户设置项。
- 打分、贪心分配、日期生成逻辑**未动**。B4 的三级检测规则**未动**。

## 3. 算法输入、输出和优先级

- **输入**：候选目的地列表（索引条目，含 `location`）、`input`（出发日期、天数、主题、季节、省份、可选 `pinned`）、可选 `geoApi`（`planner-geo.js`）。
- **输出**：与原来相同的行程草案结构（`{ok, startDate, days, itinerary, totalDays}`），仅目的地顺序（及由此决定的集合）可能变化。
- **优先级**：
  1. 用户明确指定的条件：`pinned` 顺序与保留、出发日期、天数、主题/季节/省份打分（分数分层不被地理覆盖）。
  2. 行程地理连续性：同层内最密集点出发、最近邻链；多群组时链路自然留在同一区域，不交替穿插。
  3. 其他原有逻辑：推荐权重、主题匹配、建议天数分配全部保留；不追求全局最短距离。
- **边界条件**：候选为空 → `EMPTY_RESULT`；全部无坐标 → 顺序不变；单目的地 → 不变；`pinned` 中的未知 ID 忽略，不抛错；天数 1–30 校验不变。
- **确定性**：无随机因素，同一输入两次生成结果完全相同（单测已覆盖）。

## 8. 是否出现新误报或漏报

- **无新误报**：正常短途行程（测试 2、3、4、10）零提示；同城/同省/邻省近距离均无提示。B4 检测规则未改，`b4-accept` 44 个 OK 断言全部通过。
- **无漏报**：用户明确指定的远距离目的地（pinned 拉萨+成都、浏览器插入布达拉宫）仍被 B4 检出警告/严重；编辑后插入远点仍触发严重提示，删除后提示消失。
- **测试中发现并修正的断言问题**（非产品缺陷）：`totalKm` 会被同地连住的 0km 腿稀释，不可直接对比优化前后，测试 3 改用"最大单腿距离"比较；`suggestedDays.max>1` 会使 5 天装不下 5 个目的地，测试 5 改用 8 天；无坐标目的地会正确触发 B4 的 missing 提示，测试 8 的"零提示"期望改为"仅 1 条 missing 提示"。
